# 约束工程

约束工程是把约束写进系统、而不是写进提示词的工程方法。沙箱、审批、提示词等结构性手段划定智能体的行为边界，使约束成为系统的属性，而不是模型的选择。

## 为什么需要约束

智能体能读写文件、执行命令、访问网络。若行为边界只靠提示词维持，会产生以下问题：

- 措辞冲突时，模型可能自行取舍，口头约束随时被打破。
- 模型判断失误时，越界动作没有第二道防线。

约束工程把「期望」变成「结构」：模型在约束之内自由行动，约束之外无从发生。

## 约束的分层

约束按硬度分层，越靠外层越硬，越靠内层越软：

- 环境约束：沙箱决定能访问什么，最硬。
- 决策约束：审批决定危险动作是否询问用户。
- 上下文约束：提示词与技能影响怎么做事，最软。

设计目标是让最危险的路径在最外层就被截断。

## Harness 中的约束

- 沙箱模式：read-only 只读、workspace-write 仅工作区可写、danger-full-access 全权访问。默认只读、显式放宽。
- 审批策略：ask 危险操作先询问用户，默认；never 确定性拒绝，适合无人值守。
- 提示词与技能：表达偏好与流程，适合规范做事方式，不适合作为安全边界。
- 规划模式：先提交计划、经用户批准后再执行。

## 实践原则

1. 最小权限起步：从 read-only 或 workspace-write 开始，按任务需要放宽。
2. 外层优先：能靠沙箱解决的，不要靠审批；能靠审批解决的，不要靠提示词。
3. 失败安全：默认拒绝、显式授权，无法判断时按最保守路径处理。
4. 可审计：约束的每次拦截都应能从会话日志还原。

## 反模式

- 把安全边界写进提示词：模型可违反、可漂移，无第二道防线。
- never 搭配 danger-full-access：审批与沙箱同时失效，约束形同虚设。
- 过度约束：agent 无法完成需要弹性的任务，约束沦为摩擦。
- 约束不可见：用户不知边界所在，误判 agent 的能力范围。

## 配置示例

只读审计任务的约束组合：

```yaml
dsh-sandbox-policy:
  defaultMode: read-only        # 环境约束：不可写
dsh-approval-policy:
  policy: ask                   # 决策约束：异常动作询问
```

全权开发只需把 defaultMode 改为 workspace-write，审批保持 ask。
