# 约束工程

> 约束工程（Constraint Engineering）：不依赖模型的自觉，而是把约束写进系统——沙箱、审批、工具门禁、提示词组装——用结构性手段划定智能体行为边界的工程方法。

## 为什么需要约束

智能体的自由度与风险成正比：它能读写文件、执行命令、访问网络、委派子 agent。若行为的边界只靠提示词里的"请注意不要…"来维持，那么：

- 措辞冲突时，模型可能自行取舍，口头约束随时被打破；
- 每次升级模型、更换供应商，约束效果都可能漂移；
- 一旦模型产生错误判断，越界动作没有第二道防线。

**约束工程把"期望"变成"结构"**：约束不再是模型的选择，而是系统的属性。模型在约束之内自由行动，约束之外根本无从发生。

## 约束的分层

约束按"硬度"分层——越靠外层越硬，越靠内层越软。设计约束时从外向内逐层落实：

```
┌─────────────────────────────────────────────┐
│ 1. 环境约束   沙箱、文件系统边界、进程隔离       │  ← 最硬：物理上不可达
├─────────────────────────────────────────────┤
│ 2. 执行约束   工具注册表、作用域、权限预设       │  ← 硬：能力上不存在
├─────────────────────────────────────────────┤
│ 3. 决策约束   审批策略、规划模式、人工确认点     │  ← 中：动作需授权
├─────────────────────────────────────────────┤
│ 4. 上下文约束 系统提示组装、技能、压缩策略       │  ← 软：影响判断与取向
└─────────────────────────────────────────────┘
```

一条越界路径往往要穿透多层约束才会发生；设计目标是让最危险的路径在**最外层**就被截断。

## DeepSeek Harness 中的约束面

### 1. 环境约束：沙箱模式

| 模式 | 含义 |
|------|------|
| `read-only` | 只读，失败安全（fail-safe），默认 |
| `workspace-write` | 仅工作区内可写 |
| `danger-full-access` | 全权访问，慎用 |

沙箱由 `dsh-bash-sandbox` / `dsh-sandbox-policy` 提供，是执行类工具（bash、文件读写）的实际边界。**默认 read-only、显式放宽**是环境约束的基本纪律。

### 2. 执行约束：工具注册表与作用域

- `core/tools` 维护**作用域化的工具注册表**：工具按 agent 划分作用域（`core/scope`），子 agent 只见父级授予的工具，天然实现能力最小化。
- 工具 schema 经 `core/system-prompt` 组装后才进入模型上下文——模型能调用的工具集合由系统决定，不由模型决定。
- 禁用/替换一个提供方即可整体改变能力面：把文件系统与进程提供方指向远程沙箱，Bash、PTY、LSP 便一起搬过去。

### 3. 决策约束：审批策略

| 策略 | 行为 |
|------|------|
| `ask` | 需要审批的操作先询问用户（默认；无可用 answerer 时失败关闭） |
| `never` | 确定性拒绝（CI/无人值守场景） |

`ask` 是默认的**人工把关点**：危险动作必须经过人；`never` 则把"可能危险的"整体排除，换取确定性。

### 4. 上下文约束：提示词、技能与压缩

- **系统提示组装**（`core/system-prompt`）：提示词片段按组合包逐层叠加，可在 profile patch 中注入约束性规则——这是最软的约束层，适合表达偏好与流程，不适合表达安全边界。
- **技能（SKILL.md）**：把规范、流程、检查清单固化为可加载的技能文件，把"该怎么做"约束进上下文。
- **压缩策略**（`dsh-compaction-basic`）：默认在上下文窗口 80% 时压缩、保留 16%——防止上下文失控，是资源维度的约束。
- **模型参数**：`reasoningEffort`（off/high/max）、`thinking`、`maxTokens` 约束模型的思考与输出预算。

### 5. 行为范式约束：规划模式与目标

- **规划模式**（plan mode）：要求先提交计划、经用户批准后再执行——把"先想后做"变成流程约束，而不是口头建议。
- **目标（goal）**：持久化同会话目标，支持自主轮次续跑——把长期意图固化为可追踪的约束，避免目标漂移。

## 约束工程实践原则

1. **最小权限起步**：从 `read-only` 或 `workspace-write` 开始，按任务需要显式放宽，而不是默认全权再收紧。
2. **外层优先**：能靠环境约束解决的，不要靠审批；能靠审批解决的，不要靠提示词。
3. **失败安全**：默认拒绝、显式授权；无法判断时按最保守路径处理。
4. **可审计**：会话日志"模型可见即已记录"，约束的每一次拦截都应能从日志还原。
5. **可替换**：约束通过 seam（`fs/*`、`tools/*`、`telemetry/*` 策略事件）挂载，策略本身可插拔、可升级，不依赖内核补丁。

## 反模式

| 反模式 | 问题 |
|--------|------|
| 把安全边界写进提示词 | 模型可违反、可漂移，无第二道防线 |
| `never` + `danger-full-access` | 审批与沙箱同时失效，约束形同虚设 |
| 过度约束 | agent 无法完成需要弹性的任务，约束沦为摩擦 |
| 约束不可见 | 用户不知道边界在哪，误判 agent 的能力范围 |

## 典型配置示例

一个"只读审计"任务的约束组合：

```yaml
# $DSH_HOME/settings.yaml 或 profile 的 cordis.patch.yml
dsh-sandbox-policy:
  defaultMode: read-only        # 环境约束：物理上不可写
dsh-approval-policy:
  policy: ask                   # 决策约束：异常动作询问用户
dsh-compaction-basic:
  enabled: true                 # 上下文约束：防止失控
```

一个"全权开发"任务的约束组合：

```yaml
dsh-sandbox-policy:
  defaultMode: workspace-write  # 环境约束：仅工作区可写
dsh-approval-policy:
  policy: ask                   # 决策约束：保留人工把关点
```

对比可见：约束工程的核心不是"松"或"紧"，而是**每一层都有意识地设置边界，且边界可解释、可审计**。
